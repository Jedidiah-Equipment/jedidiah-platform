# Curated Job Change Events Are `job:read`; Raw Audit Stays `audit:read`

The Job Activity feed reads what has been said about Jobs (General Feedback, ADR 0010) and, from this decision, what has been done to them. The doing is already recorded — `audit_events` carries Job creations, Job field edits, and document creations — but audit reads are gated `audit:read`, which only admins and super-admins hold, while the feed itself is gated `job:read`. A feed whose two halves disagreed on who may read them would either lock the change events away from the shop floor the feed exists for, or leak the whole audit trail to a job viewer.

We decided that **curated Job change events are part of a Job's public story and are served under `job:read`**, and that the license for it is a **projection boundary rather than a permission**: the core read `listJobActivity` selects a fixed set of audit predicates and emits typed items carrying only named fields — the actor, the Job, and a small per-type payload (the new description, the completion date, the document's filename and content type). `audit_events.changes` never crosses the API boundary from this endpoint, and a change to the audited record shape cannot silently widen what the feed exposes, because a new field reaches an item only when someone adds it to the item schema. Raw audit reads — arbitrary entities, whole change sets, the actor filter — remain exclusively `audit:read` on the `/audit` surface.

The predicate set is the policy, so it is written in one place (`pkg/core/src/job-activity/job-activity-service.ts`) and is deliberately narrow: `job` `created`; `job` `updated` where the change set names `description`; `job` `updated` where `completedOn` was set to a value; and `document` `created` where the snapshot names a `jobId`. An audit row no predicate selects is simply not part of a Job's public story. Job cancellation is the case that proves it: both cancel paths record `deleted`, no predicate matches, and cancellations therefore do not appear — a deferred decision rather than an oversight.

Two consequences we accepted:

- **Un-completing a Job produces no entry.** The completion predicate tests that `completedOn` was set to a value, not that it changed, so clearing a date is a correction rather than an event. Re-completing writes a fresh entry.
- **Document entries read their Job out of the creation snapshot, not a join to `documents`.** Documents are hard-deleted; a join would erase "this file was added" from a Job's history the moment the file went, which is the opposite of what a history is for.
- **The Brochure a Job generates for itself is excluded.** Creating a Job snapshots its Brochure through the same audited document path a person's upload takes, so the plain predicate would report a file nobody added beside every `job-created` entry. The document predicate therefore also requires that the snapshot's `metadata.type` is not `brochure`. The Product documents a Job copies at creation need no such exclusion — they are inserted without an audit event, so they never reach the feed at all.

## Considered Options

- **Per-type gating inside `jobActivity.list`** (feedback for `job:read`, change items only when the caller also holds `audit:read`) — rejected for the reason ADR 0010 rejected per-role response shaping: one endpoint whose payload varies by caller is easy to get wrong and leaks through shared caches. It also fails the purpose, since the people who work a Job are exactly the people who would not see the change events.
- **Widening `audit:read`** — rejected; it is all-entities, whole-change-set access, so it cannot express "these four kinds of Job event, these fields".
- **A second endpoint for change events with its own gate** — rejected; the feed is one ordered stream and paging it as two would either interleave wrongly or need a client-side merge, and the union contract of ADR 0010's phase-1 design exists precisely so both kinds share one list.
